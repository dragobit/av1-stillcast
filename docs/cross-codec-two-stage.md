# stillcast の二段階処理の他コーデックへの適用性分析

> 姉妹文書: [cross-codec.md](cross-codec.md) は「最終生成物（規格合法の長尺静止動画ストリーム）が各コーデックで作れるか」を扱った。本文書はもう一つの軸、すなわち stillcast の**処理アーキテクチャとしての二段階処理**——(A) エンコーダに一度だけ素材ユニットを作らせる段階と、(B) 符号化処理を一切行わずにユニットを複製・配置する段階——が同じコーデックで成立するかを扱う。
>
> 対象は前回「最終生成物が可能」と結論づけたものだけ: **VP9, H.264, HEVC, MPEG-4 ASP, MPEG-2, VP8, AV2**(仕様段階), およびコンテナ層の stts 経路。イントラオンリー系(MJPEG/PNG/FFV1/ProRes 等)と H.263 は前回不成立としたため対象外。

## エグゼクティブサマリ

二段階処理が成立するかどうかは「最終生成物が作れるか」とは別の問題で、判定条件は後者より厳しい。最終生成物を作れるだけでは足りず、**繰り返し表示ユニットが「配置だけ」で量産できること**が必要になる。この条件を「複製純度(cloning purity)」として形式化し、3 つの階級を導入した:

| 階級 | 配置操作 | 該当 |
|---|---|---|
| **純粋複製 (pure clone)** | 同じバイト列をそのまま繰り返す | VP9 / AV1(セグメント内) |
| **カウンタテンプレート (counter-template)** | 固定テンプレート + 単調増加カウンタのビット書き込み | MPEG-4 N-VOP, MPEG-2 P, VP8(要検証) |
| **条件スキーマテンプレート** | カウンタに加え、存在するフィールド自体が設定ヘッダ依存 | H.264 / HEVC スライス |
| **退化形 (degenerate)** | フレーム単位ユニット自体が不要 | mp4 stts 伸長 |

結論として**二段階処理は VP9 と H.264 で実際に動作することを本セッションで実機検証した**。VP9 は `キーフレームのバイト列をそのまま複製` + `1 バイト固定パケットを複製` だけで複数 GOP のストリームが組み立てられ、デコーダ出力は全フレームピクセル一致。H.264 も `IDR アクセスユニットのバイト複製` + `11 バイトのスキップ P スライステンプレート(フレーム番号カウンタだけを書き換え)` で 3 GOP のストリームがエラーなくデコードされた。

逆に言うと、AV1 の stillcast が持つ「エンコーダ出力から 2 ユニット(キー + ゴールデン)を採取する」入力契約は **AV1 の `showable_frame` 制約の産物**であり、他コーデックでは素材契約が「キーフレーム 1 枚 + 設定ヘッダ」に縮退する。これは二段階処理の観点ではむしろ他コーデックの方が単純である。

## 第 1 部 「二段階処理」の形式化

### 1.1 stillcast が実際にやっていること

stillcast の実装( `src/assemble.rs`, `src/segment.rs`, `src/uheader.rs`, `src/pipeline.rs` )を処理の観点で分解すると:

```
Stage A (素材製造) — 入力画像 1 枚につき 1 回だけ走る
  ├─ libaom 実エンコード → 少数 TU の AV1 ストリーム
  ├─ TU 解析: sequence header / TD / key-frame TU / golden TU を抽出
  └─ (任意) エンコーダプローブ → 再現品質 vs バイト数のコストモデル

Stage B (配置) — 出力フレーム数 N に比例するが、内容は符号化ではない
  ├─ 繰り返し指示 TU の合成: show_existing_tu() が TD+FRAME_HEADER OBU を生成(≈6 B/TU)
  ├─ ユニット配置: [seq hdr + TD + key TU + golden TU + SE TU × M] × セグメント数
  ├─ unpadded header 修復: operating_parameters の復号モデルフラグ手術
  └─ コンテナ登録: stts/stss 生成、co64 チャンクオフセット、av1C ペイロード
```

Stage B は「エンコードしない」のではなく「**エンコード済み素材の移動・複製と、狭く限定されたビットフィールドの書き込み**」を行う。この区別が他コーデックへの適用可否を分ける核心である。

### 1.2 二段階処理の必要条件

最終生成物の存在だけでは不十分で、以下の条件が揃って初めて Stage B が「符号化なしの配置」になる。

**R1. 安価な表示イベントユニットの存在**
「既デコード済みの絵をもう一度出せ」あるいは「何も変化しない絵を出せ」を指示する小さな構文ユニットが必要。AV1 の `show_existing_frame`、VP9 の同名フラグ、H.264 系列の全スキップスライス、MPEG-4 の N-VOP がこれにあたる。

**R2. エポック境界(アンカー)が複製可能であること**
任意長・任意 GOP を作るには、状態をリセットする基準ユニット(表示される KEY_FRAME / IDR / I-VOP)を**同じバイト列のまま何度でも配置**できなければならない。アンカーが自身にフレーム番号や時刻を内蔵していると複製でなくなる(後述)。

**R3. 繰り返しユニットのデコード文脈が有界であること**
繰り返しユニットが参照する状態が「直前のアンカー以降不変」であれば、アンカーごと同じ素材を繰り返せる。参照の解決方法には二系統ある:
- **スロット指名型**: 「DPB のスロット k の絵を出せ」(AV1/VP9/AV2)。スロット内容がアンカーで完全リセットされることを要求する。
- **位置型**: 「直前にデコードした参照ピクチャをコピーせよ」(H.264 スキップ, MPEG-4 N-VOP)。DPB 状態に依存しないのでアンカー要件が緩い。

**R4. Stage A で素材が採取できること**
現行エンコーダ(libaom/libvpx/x264/…)の出力から必要ユニットを切り出せること。理想は「キーフレーム 1 枚 + 設定ヘッダ」だけで済む契約。

**R5. コンテナへの登録可能性**
組み立てたエレメンタリストリームが mp4/mkv/ivf 等にマップできること。シーク用 stss エントリ、サンプル時刻表 stts、codec-private レコード(av1C/hvcC/avcC/…)の生成が要る。

**R6. 複数セグメント連結時の設定正準化**
プレイリスト連結ではセグメント間で設定系ユニット(seq header / SPS / VOL / キーフレーム非圧縮ヘッダ)がバイト一致している必要がある。Stage A のプローブはこの正準化を確認するためにも存在する。

### 1.3 「複製純度」の分類——Stage B の実装形態を決める軸

Stage B が「純粋な memcpy」で済むか、ビット書き込みを要するかは、**繰り返しユニットが自身の表示位置を示すカウンタを内蔵しているか**で決まる。

**(a) 純粋複製**: ユニット内にデコード順依存のフィールドが一切ない。バイト列が完全に不変。AV1 の SE TU は TD+FRAME_HEADER で、`frame_to_show_map_idx` はセグメント内で定数なので全 SE TU が同一バイト列。VP9 の SE パケット(検証済み `0x88`、1 バイト)はさらに極端で、ストリーム全体で定数。

**(b) カウンタテンプレート**: ユニット内に単調増加する順序/時刻カウンタがあるが、テンプレートの固定位置に書き込むだけでよい。MPEG-4 N-VOP の `time_increment`+`modulo_time_base`、MPEG-2 ピクチャヘッダの `temporal_reference`、H.264 スライスの `frame_num` がこれ。1 フレームあたりの作業は「テンプレートをコピーして数ビット書き換える」だけで、エントロピー符号化は不要。計算量は AV1 の Stage B と同じく O(1)/frame。

**(c) 条件スキーマテンプレート**: H.264/HEVC スライスヘッダが代表で、**存在するフィールド自体が SPS/PPS のフラグで変わる**。`pic_order_cnt_type` が 0 か 2 かで POC フィールドの有無が変わり、`weighted_pred_flag` で pred_weight_table の有無が、`deblocking_filter_control_present_flag` でフィルタパラメータの有無が、`entropy_coding_mode_flag` で `cabac_init_idc` の有無が変わる。実際、本セッションの H.264 検証ではこれらの条件フィールドを 4 回連続で読み違えてデコーダに拒否された(poc_type=2 への不要 POC 書き込み → field_pic_flag 誤配 → ref_pic_list_modification 順序 → pred_weight_table の分母フィールド → deblocking パラメータ)。**つまり H.264 系では Stage B に SPS/PPS パーサが前提条件として必要**であり、これは AV1 の「固定レイアウトの OBU 合成」とは質的に異なる実装コストである。逆に、一度スキーマを解決すればテンプレート化は確定的で、実行時コストは変わらない。

**(d) 退化形**: フレーム単位ユニットをコンテナ層だけで表現する。mp4 の stts delta 伸長では Stage B が「テーブルに 1 エントリ書く」だけになる。二段階処理の極限形だが、フレーム単位の GOP 構造・シーク構造は失われる。

### 1.4 Stage A の出力契約——「何枚素材が要るか」も変わる

AV1 では「キーフレーム + ゴールデン」の 2 ユニットが必須だった。理由は AV1 の `show_existing_frame` が `showable_frame` でない絵(keyframe 含む)を指せないためで、golden はこの制約を満たすために存在する。

他コーデックではこの制約が存在しないため、**素材契約が 1 ユニット + 設定に縮退**する:

| コーデック | Stage A がエンコーダから採取するもの | 繰り返しユニットの生成者 |
|---|---|---|
| AV1 | seq hdr + 表示される KEY_FRAME + golden inter | stillcast が SE TU を合成 |
| VP9 | キーフレームのみ | アセンブラが 1 バイト SE パケットを合成 |
| H.264 | SPS/PPS + IDR AU | アセンブラがスキップ P スライスをテンプレート合成 |
| HEVC | VPS/SPS/PPS + IDR | 同上 |
| MPEG-4 ASP | VOL + I-VOP | アセンブラが N-VOP をテンプレート合成 |
| MPEG-2 | GOP ヘッダ + I ピクチャ | アセンブラが P ピクチャヘッダをテンプレート合成 |

これは重要な発見である。**「エンコーダから繰り返し用ユニットを採取する」のではなく「アセンブラが繰り返しユニットを工場生産する」**のが正しい一般化であり、AV1 の golden だけが例外的にエンコーダ供給を要求する。結果として Stage A の入力契約は AV1 より他コーデックの方が緩い。

### 1.5 繰り返しユニットのビットレイアウト(実検証済み)

Stage B が「合成」または「複製」するユニットの中身を、実際に本セッションで生成・デコード確認したバイト列のレベルで示す。

**VP9 の繰り返しユニット(1 バイト定数)**

```
0x88 = 10 0 0 1 000
       │  │ │ │ └ frame_to_show_map_idx = 0(スロット 0 = 直前 keyframe)
       │  │ │ └ show_existing_frame = 1
       │  │ └ profile_high = 0
       │  └ profile_low = 0(profile 0 = 2 ビットで 00)
       └ frame_marker = 2(先頭 2 ビット)
```

keyframe 直後は全 8 スロットがその keyframe を指すので `frame_to_show_map_idx` は常に 0 でよい。

フレーム番号・時刻・サイズを一切持たないため、**この 1 バイトをそのまま何度でも並べられる**。コンテナ(IVF/mp4)がタイムスタンプを与えるだけで各パケットが 1 フレームとして表示される。

**H.264 の繰り返しユニット(11 バイトテンプレート、CAVLC)**

```
00 00 00 01 | 61 | RBSP
              │     ├ first_mb_in_slice      ue(0)
  ref_idc=3 ──┘     ├ slice_type             ue(0) = P
  type=1            ├ pic_parameter_set_id   ue(0)
                    ├ frame_num              u(4)   ← カウンタ
                    ├ num_ref_idx_active_override_flag  u(1)=1
                    ├ num_ref_idx_l0_active_minus1      ue(0) (参照=直前のみ)
                    ├ ref_pic_list_modification_flag_l0 u(1)=0
                    ├ luma_log2_weight_denom            ue(0)  ┐
                    ├ chroma_log2_weight_denom          ue(0)  │ weighted_pred_flag=1 のため必須
                    ├ luma_weight_l0_flag               u(1)=0 │
                    ├ chroma_weight_l0_flag             u(1)=0 ┘
                    ├ adaptive_ref_pic_marking_mode_flag u(1)=0
                    ├ slice_qp_delta                    se(0)
                    ├ disable_deblocking_filter_idc     ue(0)  ┐
                    ├ slice_alpha_c0_offset_div2        se(0)  │ deblocking_filter_control_
                    ├ slice_beta_offset_div2            se(0)  ┘ present_flag=1 のため必須
                    └ mb_skip_run                       ue(1600) = 全 MB スキップ
```

640×640 = 1600 マクロブロックのスキップ宣言が `ue(1600)` の Exp-Golomb 3 バイトで済むため、全体が 11 B に収まる。**太字のカウンタ `frame_num` だけを GOP 通して単調増加させればよい**——それ以外のフィールドは入力画像にも GOP 内位置にも依存しない固定値であり、これが「テンプレート + カウンタ書き込み」が成立する理由である。ただし、上のフィールドリスト自体が SPS/PPS のフラグ(`pic_order_cnt_type`, `frame_mbs_only_flag`, `weighted_pred_flag`, `deblocking_filter_control_present_flag`, `entropy_coding_mode_flag`)で変形するため、テンプレートは「設定を解決して生成する」ものであり、固定バイト列ではない。

**AV1 の繰り返しユニット(≈6 B、stillcast 現行実装)**

```
TD OBU(2 B: OBU ヘッダ + temporal_id) + FRAME_HEADER OBU(3-4 B: show_existing_frame=1 + frame_to_show_map_idx)
```

セグメント内では golden スロット番号が固定なので、全 SE TU がバイト同一 = 純粋複製。セグメントをまたぐと golden_slot が変わり得るため、テンプレートの 3 ビットだけが変わる境界は存在する。

### 1.6 複数画像プレイリストでの二段階処理

stillcast の Stage B は「1 画像 → 1 セグメント」をプレイリスト状に連結する構造も持つ(実装上、画像毎に `encode` → `make-stream` → `concat`)。二段階処理の観点では、これは **Stage A を画像数 N 回実行し、Stage B が N セグメントのバイト列を連結する**形になる。成立条件は R6(設定ユニットのバイト一致)であり、ここに面白い性質がある:

- **H.264/HEVC**: SPS/PPS の内容は画像内容に依存せず、解像度・プロファイル・レベル・エンコード設定だけで決まる。同じ設定の x264/x265 は画像が違ってもバイト同一の SPS/PPS を出す(決定的エンコーダ)ので、正準化は自動的に成立する。ただし各セグメントの先頭は IDR なので、スキップスライスの frame_num カウンタは「前セグメント最終値からの継続」か「IDR 越えのリセット許容」かを Stage B が管理する必要がある(後者は IDR 直後なら合法)。
- **MPEG-4/MPEG-2**: VOL/シーケンスヘッダも同様に設定由来で正準化可能。
- **VP9**: シーケンスヘッダが存在しないため、キーフレームの非圧縮ヘッダ(サイズ・プロファイル・色空間)が一致すればよい。同じ画像サイズ・同じエンコード設定なら一致する。
- **AV1**: seq header の一致に加え、セグメント境界で golden スロット番号が変わりうるため、SE TU の `frame_to_show_map_idx` がセグメント毎に再解決される。stillcast では golden_slot 走査がこれを担当している。

つまり**複数画像プレイリストでも二段階処理の構造は維持される**が、カウンタ管理と golden 再解決だけはコーデック別に必要になる。

### 1.7 速度特性の由来

「エンコード 1 回 + memcpy N 回」という構造が超高速の正体である。Stage B の 1 フレームあたりコストは:

- 純粋複製系: 定数バイト列の write(VP9 なら 1 B、AV1 なら ~6 B)+コンテナの stts エントリ
- テンプレート系: テンプレート ~10-20 B のコピー + カウンタ数ビットの Exp-Golomb 書き込み + (Annex-B 系は) EPB エスケープ走査

いずれもエントロピー符号化・予測・変換を含まないため、実効的にはメモリ帯域律速になる。7200 秒(30 fps で 216,000 フレーム)でも Stage B の出力は各コーデック数 MB 程度で、エンコーダを一度も起動しない。この性質はコーデックによらず、R1-R6 が満たされる限り普遍的に成立する。

## 第 2 部 コーデック別の二段階処理評価

評価項目は統一して: (1) Stage A 契約、(2) 繰り返しユニットの複製純度、(3) アンカー複製の合法性、(4) Stage B に必要なビット作業、(5) 実検証状況。

### 2.1 VP9 — 最も純粋な二段階処理 ✓実証済み

- **Stage A 契約**: キーフレームパケット 1 つだけ。`show_existing_frame` が再表示対象に showable 制約を課さないため、keyframe をそのまま指せる。非圧縮ヘッダの残り(サイズ、同期コード等)は SE パケットでは不要。
- **繰り返しユニット**: `frame_marker(2)=10, profile(1)=0, show_existing_frame(1)=1, frame_to_show_map_idx(3)` の計 8 ビット = `0x88`。**一切のカウンタを持たない**完全定数 1 バイト。
- **アンカー複製**: keyframe が全参照バッファを自身にリフレッシュするため、同じバイト列を GOP 毎に配置可能。
- **実検証**: `[KF clone] + [0x88]×3` を 2 GOP 連結した IVF(8 フレーム,57 KB)を ffmpeg でデコード → **8/8 フレームがピクセル一致、エラーなし**。別系統の検証として [research-vp9-mediabunny.md](research-vp9-mediabunny.md)(PR #51、main マージ済み)は `[KEY_FRAME, INTER]` 実エンコード出力の後に 1 B SE パケットを配置し、libvpx デコードで framemd5 が golden INTER とビット一致、WebM/MP4 remux、Chromium/Firefox で再生・シーク、Mediabunny `EncodedVideoPacketSource('vp9')` での mux まで E2E 確認している(`scripts/vp9_show_existing_poc.py`)。
- **Stage B のビット作業**: ゼロ。純粋なバイト列書き出しのみ。全コーデック中で最小実装。
- **要件の補強(KF 直後以外の SE)** — PR #51 との照合で明確化: 上の「KF 1 枚契約」は「KF が全 8 スロットを自身にリフレッシュするので SE の `frame_to_show_map_idx` は任意値で合法」に依存する。**表示対象を KF でなく INTER(golden)にする拡張形 `[anchor KF, golden INTER] + SE×N` では、SE の idx はその INTER がリフレッシュしたスロットに合わせる必要がある** — つまりアセンブラは golden INTER の非圧縮ヘッダから `refresh_frame_flags`(8 bit)をパースして採番スロットを決める。AV1 の「golden スロット走査」に相当する作業がこの場合だけ復活する(AV1 と違い必須ではなく、KF-only 構成を取れば回避できる)。また仕様 §8 上、SE が指せるのは「既にデコード済みの絵を持つスロット」のみであり、エンコーダが `show_frame=0` の隠しフレーム(alt-ref)を出した場合の pick-golden スキャンで弾く必要がある点も同文書の open questions に整理済み。
- **結論**: AV1 より単純な二段階処理。素材 1 ユニット + 定数繰り返しのみ。vp9stillcast として最も容易に移植可能な対象。

#### 補論 — 「KF-only 最小契約」と「[KF+golden INTER] 拡張形」は開発にどう効くか

まず前提の整理。AV1 の stillcast が `[seq hdr + shown KF + golden INTER]` の 3 素材契約だったのは、AV1 の SE が **`showable_frame` の絵しか指せない** ためで、KEY_FRAME は showable ではない。だから「表示される絵の資産」として INTER 系の golden が必須だった。VP9 にはこの制約がない(KF を含む任意のデコード済みスロットを指せる)ので、表示資産を別途用意する必然性が消え、**アンカーが表示資産を兼ねられる**。ここから 2 つの形が派生する:

- **形 1 (最小契約)**: `[KF] + SE×N`。KF は全 8 スロットを自身でリフレッシュするので `frame_to_show_map_idx` は任意値で合法 → SE は完全定数 `0x88`、純粋複製。
- **形 2 (拡張形)**: `[KF, golden INTER] + SE×N`。SE は INTER がリフレッシュしたスロットを指すので、idx を決めるには golden INTER の非圧縮ヘッダの `refresh_frame_flags`(8 bit)をパースする必要がある。

**開発パーツへの影響(形ごとの必要作業)**:

| stillcast のパーツ | 形 1: KF-only | 形 2: KF+golden |
|---|---|---|
| Stage A 素材採取 | KF パケットを拾うだけ。`frame_type` 1 ビットの判定 | KF + 表示される INTER の走査。非圧縮ヘッダから `frame_type`/`show_frame`/`refresh_frame_flags` をパース(AV1 の pick-golden 相当) |
| アンカー検査 | KF 非圧縮ヘッダ(geometry/colorspace)。playlist 制約に再利用 | 同左 + golden のスロット解決 |
| SE 合成 | `b'\x88'` を N 回 write。**ビットパース一切不要** | `0x88|idx` の生成 — idx を refresh flags から決定 |
| DPB 安全性 | KF 後は全スロットが同一の絵 → 常に安全 | golden より後でそのスロットを上書くフレームがないことの確認が要る(入力が [KF,INTER] 2 ユニットだけなら自明) |

**実務での使い分け**:

- **形 1 が向くケース**: 「1 フレームだけエンコードさせて素材を作る」最小構成。vp9-stillcast の第一実装はこれでよく、Stage B は `packets.extend([b'\x88'] * n)` と等価。フレーム境界は配列・IVF・Mediabunny パケットが保持するので、書き出すのは本当に定数 1 バイト×N。
- **形 2 が必要/有利なケース**:
  1. **任意のエンコード済みストリームを入力に取る場合** — 実エンコード出力は `[KF, INTER×N]` なので、AV1 の pick-golden 走査と同じ構造で golden を拾うほうが既存コードの移植面積が小さい。入力が「KF だけを取り出せる」保証がない世界で役立つ。
  2. **表示品質とアンカーの分離** — SE が表示するのはスロットの中身 = golden のデコード結果。KF を小さく低品質に、golden INTER を高品質(ロスレスに近い)にする品質レイヤリングが可能。形 1 では「表示される絵 = KF のデコード結果」に固定される。
  3. **hidden anchor 構造の再現** — AV1 式に KF を `show_frame=0` で隠して「デコードはするが表示しないアンカー」とし、表示を全て golden/SE に寄せる構成を取りたい場合(VP9 では hidden KF もスロットを埋めるので SE 経由で表示自体は可能だが、形を合わせたいとき)。
- **コスト**: 形 2 で復活する作業は「INTER 非圧縮ヘッダの `refresh_frame_flags` パース」のみ。AV1 の golden スロット走査のごく一部で、SE 自体は依然 1 B。

**メタ考察**: この分岐は「AV1 の 2 ユニット契約が `showable_frame` 制約の産物だった」ことの具体的影響。制約のない世界では「表示資産をエンコーダに別途作らせる」必要すらなくなり、アンカーがそのまま表示資産を兼ねる。形 2 は「制約がないのに AV1 の形を真似る」選択肢であり、その目的は仕様適合ではなく **コード再利用・品質分離・入力の一般化** という開発上の理由に集約される。

#### 補論 2 — シーク性能 ↔ ファイルサイズの frontier での両形評価

stillcast のコストモデル(size↔seek frontier)で両形を比較する。変数は GOP 長 \(L\)(= KF 間隔)、総フレーム数 \(F\)、GOP 数 \(G = F/L\)。

**シーク性能(両形とも同型)**:

- seek 可能点 = KF のみ。golden INTER は KF を参照するので seek 点を増やさないし、SE は delta 扱い(コンテナの sync index には KF しか載らない)。**粒度は両形とも \(L\) で完全一致**。
- seek 復元コスト = 直前 KF からの前方デコード。形 1 は `1 実フレーム + 平均 L/2 SE`、形 2 は `2 実フレーム + 平均 L/2 SE`。SE のデコードはヘッダ読み飛ばしで実質無料なので、差は golden の 1 フレーム分のデコード(ms 未満)に限られる → 実用上同一。

**サイズ式**:

- 形 1: \(S_1 = G \cdot K + F \cdot 1\,\text{B}\) — K は shown KF(=表示品質を担うので高品質必須)
- 形 2: \(S_2 = G \cdot (K_h + I) + F \cdot 1\,\text{B}\) — \(K_h\) はアンカー用 KF、`I` は golden INTER。**重要: VP9 の KF は全 8 スロットを自身にリフレッシュするため、golden は GOP をまたいで生き残れず、毎 GOP で再配置が必要**(= \(I\) は G 回現れる)。`[KF, golden, SE×N]` が GOP の繰り返し単位。

つまり両形の差は「GOP あたり \(K\) vs \(K_h + I\)」だけで、frontier の傾き(\(L\) とサイズのトレードオフ)は同じ。では \(K_h + I < K\) になり得るか:

- golden は KF の絵を参照して予測するので、**\(K_h\) を潰すと \(I\) が膨らむ** — \(K_h\) の品質が低いと golden は残差でほぼ画像を再符号化し、\(I \approx K\) に近づく。\(K_h + I\) は「表示品質の画像を 2 つのフレームに分割して運ぶコスト」なので、合計はおおむね \(K\) に収束し、せいぜい「inter モードが intra よりわずかに効率が良い」分だけ安い。**サイズの観点では両形はほぼ中立**。
- 形 2 の意味はサイズ削減ではなく**設計自由度**:
  1. \(K_h\) を `show_frame=0` の隠しアンカーにできる(AV1 stillcast と同じ構造)。表示されるのは golden のみになり、KF の品質は表示に関与しない → 「デコードさえ通ればよい」最小サイズに削る選択肢が取れる(削ると \(I\) が膨らむので正味は ± だが、エンコード条件次第では安くなる)。
  2. GOP 境界の視覚的一貫性 — shown KF と golden の品質が異なると GOP 毎に 1 フレームの品質差が点滅として見える。形 1 では shown/SE ともに同じ KF の絵なので無問題。形 2 で shown KF を使うなら品質差を揃えるか、KF を隠して「常に golden の絵」に統一するのが正しい構成。
  3. Stage A 入力が「1 フレームしかない」と制約できない場合、既存エンコード `[KF, INTER×N]` から golden を拾う形 2 が自然。
- 形 1 の実利は「パケットが GOP ごとに 1 個少ない」「解析対象が KF ヘッダ 1 種だけ」の単純さ。

**playlist/セグメント時**: 絵が変わるセグメント境界では必ず KF が要るので、セグメント数分の KF は両形で共通コスト。形 2 では golden もセグメント毎に新しいものを採取する(= \(I\) は GOP・セグメントの大きい方の頻度で現れる)。

**評価まとめ**: シーク性能は「KF 間隔 \(L\)」だけが効き、両形で完全同一。サイズは GOP あたり \(K\) vs \(K_h + I\) の差だが、参照関係の連鎖で \(K_h + I \approx K\) なので frontier 上はほぼ同一点を打つ。**したがって両形の選択は size↔seek の問題ではなく、実装構成(隠しアンカー、コード再利用、品質分離)の問題**。第一実装は形 1 が最適で、形 2 は「実エンコードを入力にする」「アンカーを表示から外したい」ときに意味を持つ拡張と整理できる。

**生成品質上の優位はあるか — 正直な答え: ほぼ無い**。エンコーダが「表示品質の KF」を出せる前提(= 1 フレームエンコード or KF だけ採取できる)が立てば、golden で表示品質を分離しても total は \(K_h + I \approx K\) で、画質が上がる構造はない。残る例外は:

- **GOP 境界の品質パルス回避** — shown KF と golden の品質が違う形 2 では GOP 毎に 1 フレームの品質差が点滅する。形 1 では shown/SE とも同じ絵なので原理的に無問題。つまり点滅回避は「形 2 の正しい運用(隠し KF)を取る理由」であって、形 2 を選ぶ理由ではない。
- **golden が KF と異なる解像度・レンダリングを持てる** — VP9 の INTER は `render_size` や参照スケーリングを持てるので、「小さいアンカー + 大きい表示絵」のような構成が原理的には可能(実用上ほぼ使われない)。
- **任意のエンコード済みストリームを入力にする場合** — 実エンコードではエンコーダが品質配分を決めており、最良の表示絵が INTER 側にあることがある。これは「入力に合わせた golden 選択」の話で、品質を作る理由ではない。
- **anchor を最悪品質に潰してもデコードは通る** — 隠し KF を max QP にしても表示は golden なので見た目は無影響だが、削った分は \(I\) が取り戻すので純粋な品質利得ではない。

つまり形 2 の「品質分離」は「品質を上げられる」ではなく「**表示品質を担うフレームとアンカーを別物にできる**」で、利点が出るのは「KF の品質を制御できない/表示したくない」ケースに限られる。

#### 補論 3 — open questions を要求項目として読む(実装に落ちる 3 点)

[research-vp9-mediabunny.md](research-vp9-mediabunny.md) が挙げる open questions は、抽象的な疑問ではなくアセンブラのコード要件に直接写る。1 つずつ見る:

**① SE は「既にデコード済みの絵を持つスロット」しか指せない(spec §8)**

- 意味: `frame_to_show_map_idx` が示すスロットに「これまでにデコードしたフレーム」が入っていることが前提。**ストリームが SE で始まることは不可能**(デコード済みの絵が無い)。stillcast の per-GOP KF 設計はこれを構造的に回避している。
- 派生 1: SE は「DPB にある絵の再表示」に過ぎないので、**SE で新しい絵を出すことはできない**。playlist で絵が変わる境界は必ず KF が要る — 「SE だけでセグメントを繋ぐ」最適化は原理的に不可能。
- 派生 2: 形 2 で golden を使う場合、SE は golden が「実際にデコードされた後」でなければならない(順序制約)。また mid-stream から読み出すデコーダは KF まで遡る必要があり、SE からの entry は仕様上も不可能 — コンテナの sync index が KF のみで正しいことが再確認できる。
- **コードへの落ち**: なし(per-GOP KF 設計で既に回避)。ただし「任意ストリームを入力にする」場合、入力の先頭が KF かは検査要。

**② `show_frame=0`(隠しフレーム)を pick-golden スキャンで弾く**

- 意味: alt-ref を使うエンコーダ(libvpx のデフォルト挙動の一部)は、参照バッファ更新だけを目的とした `show_frame=0` のフレームを出すことがある。これは「表示されなかった絵」だが **DPB スロットは占有する**。
- なぜ弾くか: 隠しフレームは SE でも表示自体は可能だが、(a)「表示を意図しない参照用の絵」は画質が異なることが多い(alt-ref は将来参照用の中間品質)、(b) そのスロットは**後続フレームに上書きされる設計**なので、SE が指す頃には別の絵に入れ替わっている危険がある。AV1 の pick-golden が `show_frame=1` のフレームを選ぶのと同じ理由。
- **コードへの落ち**: 形 1(KF-only)ではスキャン自体が不要。形 2 で任意エンコードを入力にする場合、非圧縮ヘッダの `show_frame` ビットをパースして弾く必要がある。

**③ superframe は分割必須(1 パケット = 1 フレーム)**

- 意味: libvpx は alt-ref(隠しフレーム)を直後の shown フレームと 1 パケットに束ねた superframe を出すことがあり、末尾に superframe index(各フレームサイズの表)を持つ。Mediabunny のレジストリ要件は `EncodedPacket.data` = one raw VP9 frame(§6)なので、**束ねたまま渡すと契約違反**になる。
- **コードへの落ち**: Stage A 入力で superframe を受け取ったら末尾 index を読んで個別フレームに分割して渡す(index バイトは除去)。Stage B 出力側では SE/KF を個別に emit するので superframe は自然に発生しない。alt-ref を切れば発生自体を防げる(エンコード条件で制御)。

**まとめ**: ①は「セグメント境界 = 必ず KF」と「シーク入口 = KF のみ」の根拠、②は「形 2 の golden 選択が shown フレームに限る」根拠、③は「パケット契約が 1 フレーム単位である」根拠で、いずれも「VP9 では serialization 層がなく、フレーム単位がすべて」という構造の必然的な現れ。

**形 1(KF-only)実装に限ればほぼ全て設計で回避済み**: ①は「必ず KF から emit する」不変条件を守るだけ、②は golden スキャンが存在しないので無関係(hidden KF 自身も SE 対象として合法)、③は出力側が superframe を作らないので非発生。**残る確認は入力側だけ**: Stage A を「1 フレームだけエンコードさせる」に制約すれば superframe も来ないが、任意のエンコード済みストリームを入力に取る設計にするなら「パケットが superframe なら分割」だけは残る。

### 2.2 H.264 — 条件スキーマテンプレートだが二段階は成立 ✓実証済み

- **Stage A 契約**: SPS+PPS+IDR(および任意 SEI)の 1 アクセスユニット。繰り返し用ゴールデン相当は不要(スキップは位置型参照で直前絵をコピーするため)。
- **繰り返しユニット**: `slice_type=P, num_ref_idx_l0=1(直前参照), mb_skip_run=全マクロブロック` の全スキップ P スライス。実測 640×640 で **11 B/フレーム**(Annex-B)。ただし `frame_num` をスライス毎に単調増加させる必要があり、純粋複製ではなくカウンタテンプレートになる。
- **アンカー複製**: IDR AU のバイト列をそのまま複製可能(IDR は frame_num=0 固定 + DPB リセットで自己完結)。実検証では同一 IDR バイト列を 3 回配置し、それぞれにスキップ 2 枚を接続 → ffmpeg が 3 IDR + 6 P を**エラーなくデコードし、全出力がピクセル一致**(末尾に +1 フレームの drain 出力が出る ffmpeg 特有の現象あり、内容は同一)。
- **Stage B のビット作業**: 軽いが**条件付きフィールドの解決が前提**。本検証で判明した依存: `pic_order_cnt_type=2` → POC フィールド非存在、`frame_mbs_only_flag=1` → フィールドフラグ非存在、`weighted_pred_flag=1` → pred_weight_table(分母 ue ×2 + フラグ ×2)必須、`deblocking_filter_control_present_flag=1` → フィルタ idc+αβ オフセット必須、CAVLC → `cabac_init_idc` 非存在。すなわち Stage B は SPS/PPS からスキーマを解決するミニパーサを持つ必要がある。加えて出力は EPB(0x000003 挿入)処理が要る。
- **注意点**: CABAC 系では `mb_skip_run` が使えず、MB 毎のスキップフラグを CABAC エンコードする必要があるため 11 B→~200-400 B に膨らむ。このため二段階処理としては **CAVLC + baseline/main 系プロファイルに限定**するのが実用的。既存エンコーダから採取するのではなくアセンブラがスライスを生成するので、これは選択可能。
- **結論**: 実装コストは最大だが、AV1 に次ぐ本命。Stage A の契約はむしろ最も緩い(IDR 1 枚)。プロファイル是正とスキーマ解決が実装の核心。

### 2.3 HEVC — H.264 と同型で実装コストだけ高い

- **Stage A 契約**: VPS+SPS+PPS+IDR(IRAP)1 AU。
- **繰り返しユニット**: 全 CTU が skip の非 IRAP スライス。H.264 と同じ位置型参照(直前ピクチャをデフォルトで参照)。スライスヘッダに `slice_pic_order_cnt_lsb` を持つためカウンタテンプレート。
- **アンカー複製**: IDR/CBLA は DPB をリセットするためバイト複製可能。
- **Stage B のビット作業**: H.264 より広いが構造は同型。SPS のフラグ群(`sps_temporal_mvp_enabled`, `strong_intra_smoothing`, `weighted_pred`, `deblocking_filter_control_present`, `loop_filter_across_slices` …)でスライスヘッダのフィールド集合が変わる点も同じ。
- **注意点**: デコーダ実装が x265 系のデフォルトで `pic_output_flag` 等を出す場合の互換リスクと、ステータスとしてコンテナ(hvcC)登録までの整備度が H.264 より劣る。
- **結論**: 二段階処理は成立する見込みが高いが、検証コストと実装コストの割に互換性メリットが H.264 に負ける。

### 2.4 MPEG-4 Part 2 ASP — 構文は最小だがデコーダ互換性がネック

- **Stage A 契約**: VOL ヘッダ + I-VOP 1 枚。
- **繰り返しユニット**: `vop_coded=0` の N-VOP。「前の表示 VOP と同じ絵を出せ」という位置型の表示指示で、スキップテンプレートすら不要な純粋な表示制御。ただし `modulo_time_base` と `time_increment` のカウンタを持つのでテンプレート系。
- **アンカー複製**: I-VOP を毎 GOP で複製可能だが、I-VOP 自身も `time_increment` を持つため、厳密にはアンカーもカウンタ書き込みが必要なテンプレートになる(VP9/AV1/H.264 との差異)。
- **実検証**: N-VOP(パケット ~7 B)を正しい時間進行で 30 個連結 → ffmpeg の mpeg4 デコーダは**パケットを受理するが vop_coded=0 に対して出力フレームを生成しない**(30 パケット → 1 出力)。つまり二段階処理の「ストリームとしての合法性」は満たせるが、デコーダ実装依存で出力が得られない。
- **結論**: 構文的には最もシンプルな二段階処理(繰り返しユニットが専用の表示制御)だが、実装系の互換性で実用的でない。デコーダ別に要検証。

### 2.5 MPEG-2 — 放送運用系では二段階処理が既に実用化されている

- **Stage A 契約**: GOP ヘッダ + I ピクチャ(シーケンスヘッダ内蔵)。
- **繰り返しユニット**: picture_coding_extension の `repeat_first_field` フィールドで 1.5x 表示の伸長が可能で、これは放送 TS でフィルム素材を送るための標準的手法。**ただしこれは有限伸長であり、任意反復は作れない**。任意長を作るには「全マクロブロックが not_coded の P ピクチャ」(全スキップ P)を使う。MPEG-2 の P ピクチャは `temporal_reference` カウンタを持つため、テンプレート系。
- **アンカー複製**: I ピクチャは self-contained だが GOP ヘッダの `time_code` カウンタがある(放送規格では連続を要求するが、デコーダ依存で飛んでも動くことが多い)。I ピクチャ内にも temporal_reference があるのでテンプレート扱い。
- **結論**: 二段階処理の構造は成立するが、GOP 構造が「I のみ複製 + P テンプレート」という形になり、繰り返し単位のサイズが AV1 より大きい(テンプレート P ピクチャは ~30-100 B 程度)。対象としては古い規格で TS 系の検証が必要。

### 2.6 VP8 — おそらく純粋複製だが検証未完・優先度低

- **Stage A 契約**: キーフレームパケットのみ。
- **繰り返しユニット**: VP8 の非圧縮フレームヘッダには**フレームカウンタが存在しない**(frame_tag に part size と intra/inter フラグ、以降は show_frame, refresh flags, filter params, segmentation …)。全スキップ P(全マクロブロック implicit-skip + no residual)を生成すれば、同じバイト列が毎フレーム合法になる可能性が高い。
- **課題**: エンコーダ(libvpx)のデフォルト出力は既に ~183 B/フレーム(実測)で、手作りテンプレートの正当性は未検証。また AV1/VP9 と違い show_existing_frame のような表示指示がなく、スキップスライス系の解釈に依存する。
- **結論**: 構造的には純粋複製の可能性があるが、エコシステムが旧規格で移植メリットが乏しいため今回は検証を行わなかった。

### 2.7 AV2(AVM) — 仕様上は AV1 と同型だが実装未成熟

- AV2 仕様 v1.0.0 は `OBU_REGULAR_SEF` / `OBU_LEADING_SEF` として show_existing_frame 相当を保持する(Web 検証済み)。したがって二段階処理の構造は AV1 と同型で成立する見込み。
- ただし AVM 参照実装はまだ安定しておらず、実検証(Stage A 供給およびデコード確認)は現時点で行えない。AV2 対応が実用化段階に入れば、stillcast の二段階処理はおそらく最もそのまま移植できる。

### 2.8 mp4 stts 経路 — 二段階処理の退化形

- **構造**: Stage A が 1 サンプル(任意のコーデックのイントラ絵)を生成、Stage B が「stts の delta を巨大にする」だけのメタデータ操作。**フレーム単位ユニットを一切生成しない**ため、最も極端な二段階処理。
- **利点**: コーデック非依存で汎用的かつ Stage B が O(1)。**欠点**: GOP 構造・シーク粒度・フレーム単位の期間制御が失われ、デコーダが 1-2 フレームしか出さない実装もある(検証済み)。stillcast がこの道を選ばなかったのは、ビットストリーム層でフレームを生成する方が最大公約数的な互換性を持つため。
- **結論**: 「ビットストリーム層でフレームを量産する」という stillcast の要件からは外れるが、二段階処理の最も軽い実装形態として参照価値がある。

## 第 3 部 横断分析——二段階性を分ける構文特性

### 3.1 カウンタの内包が clone を分ける

繰り返しユニットが「いつ表示されるか」の情報を持つかが決定的に重要である:

- **持たない**(AV1 SE, VP9 SE): コンテナが時刻を与えるだけで良い → 純粋複製
- **持つ**(H.264 frame_num, MPEG-4 time_increment, MPEG-2 temporal_reference, HEVC poc_lsb): 単調増加が必須 → テンプレート化

これは「デコーダがフレームの表示順・時刻をエレメンタリストリームだけから再構成しようとする」設計の遺産で、古いコーデックほどこのカウンタを持つ傾向がある。AV1/VP9 は「表示指示のみをエレメンタルに、時刻はコンテナに」と分離した設計であり、これが純粋複製を可能にしている。

### 3.2 参照解決: スロット指名 vs 位置参照

- **スロット指名**(AV1, VP9, AV2): DPB の特定スロットを示すので、参照先がアンカーのリセット内容に依存する。AV1/VP9 の keyframe は全スロットを自身にリフレッシュするので、`frame_to_show_map_idx=0`(固定)で常に最後の keyframe を指せる。**アンカーが「同じバイト列で状態を完全リセットする」性質が複製の根拠**になる。
- **位置参照**(H.264, HEVC, MPEG-4): 「直前にデコードした参照ピクチャ」を指すので、DPB スロットの内容を意識しない。アンカーがスロットリセットをしなくても繰り返しは機能する。結果として**位置参照系はアンカー要件が緩い**(非 IDR の I でも構わない)が、スロット指名型は「毎 GOP で同じリセットを起こすアンカー」を要求する。

### 3.3 アンカーの自己リセット性

繰り返し可能な GOP 構造を作るには、アンカーユニット自身がバイト複製可能でなければならない:

| コーデック | アンカー | カウンタ内包 | 複製可能 |
|---|---|---|---|
| VP9 | keyframe | なし | ◎ |
| AV1 | shown KEY_FRAME | なし | ◎ |
| H.264 | IDR AU (SPS/PPS 内包) | frame_num=0 固定 | ◎ |
| MPEG-4 ASP | I-VOP | time_increment 内包 | △(テンプレート) |
| MPEG-2 | GOP+I ピクチャ | time_code + temporal_reference | △(テンプレート) |

MPEG-4 と MPEG-2 ではアンカー自身がカウンタを持つため、二段階処理のアンカー段でもテンプレート化が必要になる。これは実装コストの差として現れる。

### 3.4 Stage B の実装コストの構成要素

コーデック別に Stage B がやるべき作業を分解すると:

| コーデック | ユニット生成 | カウンタ書き込み | 設定修復 | 直列化層の仕事 |
|---|---|---|---|---|
| VP9 | 定数 1 B の write | なし | なし | なし |
| AV1 | SE TU 生成 | なし(同一バイト列) | uheader 復号モデルフラグ手術 | OBU の leb128 パッチ |
| H.264 | スキップスライス生成 | frame_num, (poc_lsb) | SPS/PPS スキーマ解決 | EPB エスケープ + AU 長接頭辞 |
| HEVC | スキップスライス生成 | poc_lsb 等 | VPS/SPS/PPS スキーマ解決 | EPB エスケープ + AU 長接頭辞 |
| MPEG-4 | N-VOP テンプレート | time_increment | VOL 解決 | なし |
| MPEG-2 | P ピクチャテンプレート | temporal_reference | GOP ヘッダ time_code | なし |
| mp4 stts | なし(1 サンプル) | なし | なし | なし(メタデータのみ) |

Stage B の実装難易度は VP9 < AV1 < MPEG-4 < MPEG-2 < H.264 ≈ HEVC の順になる。

### 3.5 Stage A のコストモデルと決定性

stillcast の Stage A は「実エンコーダを走らせて素材を採取する」だけでなく、エンコーダ出力のコストモデル(再現品質 vs バイト数)を持つ。これは「決定的な設定でエンコーダをプローブして特性を測る」ことに依存する。幸い、主要エンコーダはいずれも決定的である:

- libaom(AV1): 決定的(スレッド毎でも再現可能)
- libvpx-vp9: 決定的
- x264: 決定的(threads によらず同一設定で同一出力)
- libxvid(MPEG-4): 決定的
- x265: 概ね決定的(WPP 設定による)
- FFmpeg mpeg2video: 決定的

したがって「同じ画像・同じ設定なら同じバイト列の素材が得られる」という Stage A の前提はコーデック非依存で成立し、stillcast のコストモデル設計はそのまま移植できる。

### 3.6 複数セグメント連結の正準化

AV1 では全セグメントで seq header がバイト一致する必要がある(そうでないとデコーダが別シーケンスと認識する)。同様に:

- H.264/HEVC: SPS/PPS の sps_id/pps_id と内容が一致する必要。x264 の同じ設定なら同じ SPS/PPS が出るので問題ない。
- MPEG-4: VOL ヘッダの一致。
- MPEG-2: sequence header の一致。
- VP9: シーケンスヘッダ相当が存在しないため、キーフレーム非圧縮ヘッダ(サイズ・プロファイル・色彩情報)の一致に帰着する。

### 3.7 失敗条件——二段階処理を壊すもの

- 繰り返しユニットが**毎フレームのエントロピー符号化を要求**するコーデック(イントラオンリー系: MJPEG, PNG, ProRes, FFV1 等)では Stage B が成立しない。
- 繰り返しユニットが**前フレームとの差分エンコードを強制**し、かつ skip が不可能な設計だと成立しない(VP8 はこの境界にあるが、実測では all-skip が合法)。
- DPB リセットが部分的で、繰り返しユニットが参照する状態がリセットされないコーデック(AV1 の INTRA_ONLY がスロットを全リフレッシュしないケース)。
- 繰り返しユニットが**依存コンテキストを持つ**場合。例えば AV1 の SE TU が依存するのは「golden スロットに有効な絵がある」ことだけであり、これは KEY_FRAME のリセットで満たされる。もし SE TU が前フレームの MV や residual を参照する設計だったら複製は不可能だった。

## 第 4 部 stillcast 手法の一般化定義

前項を踏まえ、stillcast の手法をコーデック非依存の形で言い直すと:

> **「素材供給はエンコーダに 1 回だけ行わせ、配置はビットストリーム構文の繰り返し表示プリミティブを素材として量産し、コンテナに登録する」**

この定義に含まれる設計決定は:

1. **素材はエンコーダ由来、配置はアセンブラ由来**: エンコーダはピクセル → エントロピー符号化の仕事に限定し、表示構造の制御はアセンブラがビットストリーム構文で直接行う。
2. **繰り返しユニットはアセンブラが生成する**: AV1 の golden のようにエンコーダが供給するのは例外。正しい一般形は「アセンブラが繰り返しユニットを工場生産する」。
3. **繰り返しユニットは「表示イベント」であり「画素データ」ではない**: 「既にデコードした絵を出せ」「何も変わっていない絵を出せ」を構文的に表現するユニットを要求する。
4. **エポック構造**: 表示絵が変わる境界(アンカー)で自己リセットするユニットを用い、エポック間で同じ素材を再利用する。
5. **コンテナ登録は最小限のメタデータで**: シークとタイミングはコンテナ層が担当し、エレメンタリストリームは純粋に表示イベントの列になる。

この一般化に立つと、**「コーデックが二段階処理に適するか」は (a) 表示イベントプリミティブの有無、(b) そのプリミティブのカウンタ内包の有無、(c) アンカーの自己リセット性、(d) 設定ユニットの正準化可能性——の 4 点で判定できる**。複製純度分類はこのうち (b) を直接反映している。

## 第 5 部 検証結果(本セッション)

### 5.1 VP9 — 純粋複製二段階処理の実証

```
[KF clone] [SE] [SE] [SE] [KF clone] [SE] [SE] [SE]   (KF = 27.8 KB, SE = 1 B)
```
を IVF に格納 → ffmpeg(vvdec ではなくネイティブ vp9 デコーダ)でデコード:

- 8 フレーム全てピクセル一致(`YUV` 比較で全バイト同一)
- デコードエラーなし

**Stage A**: libvpx が生成した keyframe パケットのみ採取。**Stage B**: KF を複製 2 回 + `0x88` を複製 6 回。**符号化処理ゼロで 2 GOP のストリームが完成した**。

### 5.2 H.264 — 条件スキーマテンプレート二段階処理の実証

```
[SPS/PPS/SEI/IDR clone] [skip P: fn=1] [skip P: fn=2]
[SPS/PPS/SEI/IDR clone] [skip P: fn=3] [skip P: fn=4]
[SPS/PPS/SEI/IDR clone] [skip P: fn=5] [skip P: fn=6]
```
を Annex-B H.264 として格納 → ffmpeg デコード:

- 3 IDR + 6 skip-P を受理、`no frame!` エラーなし(9 パケット → 9 coded フレーム、ffmpeg が末尾に +1 フレームを drain して 10 フレーム出力、全てピクセル一致)
- skip P スライスは **11 B**(`00 00 00 01` 4 B + NAL ヘッダ 1 B + RBSP 6 B)
- IDR AU はバイト列の完全複製(27.8 KB × 3)

**Stage A**: x264 の SPS/PPS+IDR AU のみ採取。**Stage B**: IDR 複製 + 11 B テンプレートに frame_num を書き込み。ただしテンプレートのフィールド集合は SPS/PPS のフラグに依存し、実際に 4 回の仕様読み違い(poc_type=2 に POC 書き込み, field_pic_flag の誤配, ref_pic_list_modification の順序, pred_weight_table の分母, deblocking パラメータ)を経て正当な構造を確定した。この過程自体が「H.264 の Stage B は SPS/PPS スキーマ解決を必須とする」という実証である。

### 5.3 対応する GOP 構造の自由度

- VP9: KF の間隔(= GOP 長)は任意。SE 数 = GOP 長 - 1 で自由に設定可能。
- H.264: IDR の間隔は任意。skip-P の個数 = GOP 長 - 1。frame_num は単調であれば良い(実検証では GOP 越えて連番)。IDR で POC もリセットされるので、連番を維持するだけで整合する。

両者とも「任意長・任意 GOP」を Stage B のパラメータだけで実現でき、AV1 と同じ自由度を持つ。

## 第 6 部 結論と移植ロードマップ

### 6.1 Tier 分け(二段階処理適合度)

| Tier | コーデック | 複製純度 | Stage A 契約 | 実装コスト | 検証状況 |
|---|---|---|---|---|---|
| **T1** | **VP9** | 純粋複製 | KF 1 枚のみ | 最小 | ✓ 実証 |
| **T1** | **H.264** | 条件テンプレート | IDR 1 枚のみ | 中(SPS/PPS スキーマ) | ✓ 実証 |
| T1.5 | AV2 | おそらく純粋複製 | KF + golden 系 | 小(AV1 と同型) | 仕様のみ |
| T2 | HEVC | 条件テンプレート | IDR 1 枚 | 中-高 | 構造確認 |
| T2 | MPEG-4 ASP | カウンタテンプレート | I-VOP 1 枚 | 小(構文) | 構文可・デコーダ互換× |
| T2 | MPEG-2 | カウンタテンプレート | I 1 枚 | 中 | 放送系経路の実績あり |
| T3 | VP8 | おそらく純粋複製 | KF 1 枚 | 小 | 未検証・優先度低 |
| T3 | mp4 stts | 退化 | 1 サンプル | 最小 | ✓ 実証(但し非 GOP) |

### 6.2 AV1 stillcast から何が移植できるか

**そのまま移植できるもの**:
- 二段階処理のアーキテクチャ全体(Stage A/Stage B の分離)
- エンコーダプローブによるコストモデル(決定的エンコーダで再現可能)
- セグメント正準化チェック
- コンテナ登録層(stts/stss 生成)
- 「表示イベントと画素データの分離」という設計思想

**AV1 固有で移植されないもの**:
- golden フレームという第 2 素材概念(showable_frame 制約の産物、他コーデックでは不要)
- decoder-model フラグの unpadded ヘッダ手術(AV1 の uheader 特有)
- sequence header 正準化(AV1 の seq hdr に特有の制約)

**新たに必要になるもの**:
- VP9: 実質的に追加の仕事はほぼない。AV1 の assemble ロジックを簡素化したもので足りる。
- H.264/HEVC: SPS/PPS のスキーマ解決パーサ + Annex-B/AVCC の直列化 + EPB エスケープ。
- MPEG-4/MPEG-2: カウンタフィールドのテンプレートエンジン。
- 全般: 繰り返しユニット生成器(コーデック毎に異なるが、すべてアセンブラ内部実装)。

### 6.3 推奨実装順序

1. **VP9**: 二段階処理の純粋形をまず実装。`keyframe 1 枚採取 + 定数パケット複製` で、stillcast の構造を最もシンプルに再現できる。検証も容易。
2. **H.264**: 互換性が最大の対象。SPS/PPS パーサが必要になるが、libavcodec/h264 の仕様書は整備されており、スキーマ解決の実装は一度書けば再利用できる。CAVLC + baseline/main に限定すると実装が簡潔になる。
3. (将来) **AV2**: 参照実装が安定した時点で AV1 から直移植。

HEVC は H.264 と構造は同型だが、互換メリットが H.264 に及ばないため優先度は低い。MPEG-4 と MPEG-2 はレガシー系として需要があれば対応可能だが、実装系の互換リスクが残る。

## 付録 A. 検証コマンド

```bash
# Stage A: 素材生成(1 枚画像 → 60 フレーム x264 CAVLC)
ffmpeg -y -loop 1 -i jacket.png -vf format=yuv420p -r 30 -frames:v 60 \
  -c:v libx264 -crf 28 -bf 0 -coder 0 h264_cavlc.mp4
ffmpeg -y -i h264_cavlc.mp4 -c:v copy -bsf:v h264_mp4toannexb h264_ab.h264

# Stage B: IDR AU 複製 + 11B skip-P テンプレート(frame_num だけ書き換え)
# → 3 GOP / 9 パケット、ffmpeg デコードで全フレーム一致を確認
ffmpeg -y -i h264_2gop.h264 -pix_fmt yuv420p out.yuv -f null -

# VP9: KF パケット + 0x88 SE パケットの複製 → 2 GOP/8 フレーム
ffmpeg -y -i vp9_2gop.ivf -pix_fmt yuv420p out.yuv -f null -
```

## 付録 B. 前提知識

- AU = Access Unit(1 表示フレームに対応する NAL 集合)
- DPB = Decoded Picture Buffer(デコーダ内部の参照バッファ)
- OBU/TU = AV1 の構文単位
- NAL = Network Abstraction Layer(H.264/HEVC のユニット単位)
- SE = show_existing_frame(繰り返し表示指示)
- EPB = Emulation Prevention Byte(H.264 系で 0x000003 を挿入するエスケープ)
- VOL = Video Object Layer(MPEG-4 のシーケンスヘッダ相当)
- GOP = Group of Pictures(アンカーから次のアンカーまでの区間)

## 付録 C. 未検証リスク

- VP8 の全スキップ P は非圧縮ヘッダにフレームカウンタを持たないと推測されるが、実装(ffmpeg/libvpx デコーダ)でまだ確認していない。
- AV2 の OBU_REGULAR_SEF の詳細フィールドと、golden 相当の制約が AV1 と同一かは仕様テキストのみに基づく。
- MPEG-4 の N-VOP を正しく出力するデコーダ実装(ffmpeg は不可)の存在は未確認。理論上 libavcodec の mpeg4 以外(GStreamer の avdec, DivX, Xvid 独自実装)で挙動が異なる可能性がある。
- HEVC のスキップスライスによる二段階処理は構造的に可能だが、x265 や MainConcept 系デコーダでの実検証は未実施。
- MPEG-2 の temporal_reference テンプレートは、放送系 TS 規格での連続性要求が厳格かどうかで合法性が変わる可能性がある。
