# AV1 にあって VP9 にないもの — 実用ユースケースから見た能力差分

> 姉妹文書: [cross-codec.md](cross-codec.md) で「VP9 にも `show_existing_frame` が存在し、stillcast の中核トリックはむしろ VP9 の方が簡単」と判明し、[vp9-layers.md](vp9-layers.md) で「VP9 は AV1 より 1 層少ない世界」と構造差を整理した。では逆方向の問い —— **AV1 が持ち、VP9 が持たない/不得意な能力は何か** —— はまだ網羅されていない。本文書はこれを、符号化ツール・ビットストリーム構文・エコシステムの 3 層で、実用ユースケースとの対応付きで整理する。「なぜ stillcast が AV1 主力なのか」「VP9 版を出す意味はどこに残るか」の判断材料である。

## エグゼクティブサマリ

| 層 | AV1 にあるもの | VP9 の状況 | 直結する実用ユースケース |
|---|---|---|---|
| イントラ予測 | 56+ 細角度方向 + PAETH/SMOOTH/FILTER_INTRA + **CfL(輝度から色度を予測)** | 10 モードのみ | キーフレーム品質、AVIF、静止画主体コンテンツ |
| インター予測 | **コンパウンド予測**(2 参照・複数ブレンド式)、明示的 **7 参照選択**、**ワープド/グローバルモーション**、skip_mode、MV 場投影 | 単方向・3 固定参照のみ。コンパウンドなし | 階層 GOP、カメラパン/ズーム、スライドショーの動き |
| 変換・分割 | 16 変換種(IDTX/FLIPADST 系含む)、**128×128** ブロック、T 字・4:1 矩形分割 | 4 変換種、64×64、2:1 矩形まで | 高解像度・大域的な滑らか勾配 |
| ループ内修復 | デブロック + **CDEF + Loop Restoration + superres + フィルムグレイン合成** | ループ内デブロックのみ | 低ビットレート配信、映画の粒子保持、擬似高解像度化 |
| 量子化 | **qmatrix**(係数毎の重み行列)、ブロック毎 delta_q、U/V 独立 q | セグメント毎 q のみ | 視覚重み付け量子化、良質なレート制御 |
| スクリーンコンテンツ | **palette モード / intrabc**(画面内ブロックコピー) | 該当機構なし | 画面共有、UI 録画、ゲーム/プレゼン |
| ユニット構造 | **OBU の型付きユニット層** + metadata OBU(MDCV/CLL/T.35)、TD、**Annex-B** | 型付きユニット無し、メタデータ経路なし、規格直列化なし | HDR 配信、中間処理ツール、規格準拠 |
| 時間・層構造 | **decoder model**(バッファ規格)、timing info、operating points、**scalability metadata**、**switch frame** | バッファモデルも層構造信号も無し | SVC 会議/SFU、放送、準拠検証、シーク高速化 |
| 静止画 | **still_picture / reduced_still_picture_header**、AVIF | 規定なし(WebP は VP8 系) | 静止画フォーマットとしての採用 |
| 実装系 | libaom / SVT-AV1 / rav1e + dav1d + **HW エンコード普及** | libvpx 一本、HW エンコード実質なし | ライブ配信・リアルタイム・録画 |

圧縮効率そのもの(同画質で VP9 比おおよそ 2〜3 割減)は有名なので本書では脇に置き、**「 VP9 では原理的に作れない/表せないもの」**を中心に据える。

## 1. 符号化ツール層 — 画質・適用範囲の差

### イントラ予測:静止画・キーフレーム品質の地力

- **方向予測の密度**: VP9 のイントラは 10 モード(DC, TM, V, H, D45 等の粗い 6 方向)。AV1 は 8 基準方向に ±4 ステップの細角度を掛け、実効 **56 方向超**。斜めエッジを持つ画像(ロゴ、タイポグラフィ、イラスト)の残差が大幅に減る。
- **PAETH / SMOOTH / FILTER_INTRA**: 勾配の滑らかな面や、フィルタ済み参照画素による予測は VP9 に存在しない。
- **CfL (Chroma from Luma)**: 再建済み輝度ブロックから色度を線形予測する。VP9 は色度を独立にしか予測できない。高彩度のエッジ(色文字、UI)で差が出る。

stillcast 目線では「1 枚のキーフレームの符号化効率」に直結する。静止画単体なら AVIF としても流通する AV1 イントラの方が、同サイズで明らかにきれい。

### インター予測:VP9 は「片方向しか見られない」

- **コンパウンド予測**: AV1 は 1 ブロックに 2 参照を許し、ブレンド式も average/distance-weighted/difference/wedge マスク/inter-intra から選べる。**VP9 にはコンパウンド予測自体が存在しない** —— LAST/GOLDEN/ALTREF の 3 参照インデックスは「どれか 1 枚」を指すだけで、双方向予測は不可能。H.264 の B フレームに相当するものが VP9 では式として書けない。
- **7 参照の明示選択**: AV1 は 8 バッファから LAST, LAST2, LAST3, GOLDEN, BWDREF, ALTREF2, ALTREF の 7 系統をフレーム毎に任意選択できる。VP9 の参照は固定 3 役職。この差で AV1 は階層参照構造(複数段の altref/B フレーム相当)を自由に組める。
- **ワープドモーション/グローバルモーション**: アフィン変換(回転・ズーム・せん断を含む)による動き補償。カメラのパン・ズーム・手ブレを *ブロック MV ではなく行列*で表せる。VP9 は平行移動 MV(最大 1/8 画素精度)のみ。静止画のスライドショーに「ゆっくりズーム/パン」を載せる演出は、AV1 ならグローバルモーション一発でほぼゼロコストに近い —— stillcast が将来「動く静止画」を扱う時の伏線になる。
- **skip_mode / MV 場投影 (ref_frame_mvs)**: 隣接 MV と過去フレームの MV 場から MV を推定し、MV 自体を送らない選択肢。VP9 は空間近傍のみ。
- **デュアル補間フィルタ**: AV1 は水平・垂直で別フィルタを選べる(双方向で異なるタップ数含む)。VP9 はブロック毎 1 フィルタ。

### 変換・ブロック分割

- AV1 は変換種が 16(DCT, ADST/FLIPADST の方向別組合せ, IDTX 等)でブロック形状に応じ選択。VP9 は 4 種(DCT/ADST 系)+ロスレス用 WHT。
- 最大ブロック **128×128**(VP9 は 64×64)。大きな平坦面・高解像度ほど効く。
- 分割形状は T 字分割(HORZ_A/B, VERT_A/B)と 4:1/1:4 矩形を持ち、VP9 の「正方形を 4 等分 or 2:1 横/縦割り」のみより、物体境界へのフィットが良い。

### ループ内修復パイプライン — 低ビットレートで最大の差

VP9 のループ内処理はデブロッキングフィルタ 1 本のみ。AV1 はデブロックの後に:

1. **CDEF**(方向制約付きディザ/リンギング除去): エッジ方向を推定してその方向だけフィルタし、リング状ノイズを消す。
2. **Loop Restoration**(Wiener or 自己ガイド付き投影): 劣化したテクスチャを参照構造から「修復」する。
3. **superres**: デコードループ内で水平方向を拡大再構成する(符号化時は低解像度、表示時に高周波を合成)。
4. **フィルムグレイン合成**: エンコード時に粒状ノイズをモデル化して除去し、デコード側で再合成する。**粒子は運ばず「パラメータ」だけ運ぶ**。VP9 に相当機構は皆無。

この積層のおかげで、AV1 は「低ビットレートで壊れ方が上品」になる。Netflix が AV1 を推した実用上の理由の半分はフィルムグレイン + 修復系といってよい(粒子の多い実写素材で VP9 的なエンコードは粒子をブロックノイズに変える)。

### 量子化

- **qmatrix**: 変換係数毎の重み行列をセグメント・リファレンス種別毎に選べる。視覚的に重要な低域を守り高域を捨てる設計が構文で表せる。VP9 は係数一括量子化。
- **delta_q**: スーパーブロック毎の符号付き q 調整を算術符号化する。VP9 は 8 セグメント単位でのみ調整可能。

### スクリーンコンテンツ — VP9 が構造的に白旗な領域

- **palette モード**: ブロック内の色をパレット化しインデックスを送る。文字・UI・図形に極めて強い。
- **intrabc**: 同一フレーム内の既再建領域をブロックコピー参照する(実質「フレーム内での LZ77」)。繰り返し UI 要素・等幅テキストに劇的に効く。

VP9 には両方とも無い。WebRTC の画面共有で Chrome が AV1 モードを載せた理由はほぼこの 2 つ。

## 2. ビットストリーム構文・シグナリング層 — 「運べる情報」の差

[vp9-layers.md](vp9-layers.md) で確立したとおり、VP9 は型付きユニット層を持たず、全情報がフレーム非圧縮ヘッダに同居する。これが以下の全ての差の母胎になる。

### メタデータの搬送路

AV1 の metadata OBU は型別に HDR 動的メタデータ(ITU-T T.35)、**MDCV( mastering display colour volume )**、**CLL(content light level)**、scalability、timecode を運べる。

- **HDR**: AV1 は `color_config`(色域・伝達関数・行列係数の完全な BT.2020/2100 シグナリング)+ 静的 HDR メタデータ(MDCV/CLL)+ T.35 経由で **HDR10+/Dolby Vision** を運べる。VP9 のヘッダには色空間列挙と量子化レンジ程度しかなく、**伝達関数(PQ/HLG)も HDR メタデータも運べない**。YouTube の VP9 HDR はコンテナ(WebM)側の拡張で糊付けしていた経緯がある。規格上「HDR を運ぶビットストリーム」は AV1 でしか作れない。
- **拡張性**: 将来のメタ型が OBU type を足すだけで済むのに対し、VP9 は「フレームヘッダに新フィールドを生やす」以外の手段がない。

### 直列化と中間処理

- **Annex-B**: AV1 には規格化された長さ区切り直列化(annexb)があり、ストリーム切断・再同期・中間フィルタリングが規格レベルで書ける。VP9 には**規格直列化が存在しない**(生圧縮フレーム列は自己区切りでなく、実用上 IVF かコンテナを要求される —— vp9-layers.md 実測どおり)。
- **Temporal Delimiter / padding OBU**: 可視フレームを持たない制御情報をストリームに差し込める。VP9 では不可能。

### 時間構造と層構造

- **decoder model / timing info**: AV1 はシーケンスヘッダに HRD 的なデコーダバッファモデルと時刻情報を内蔵でき、バッファアンダーフローの適合性判定ができる。VP9 仕様にバッファモデルはない → **放送・規格準拠が要求される領域は AV1 しか書けない**。
- **operating points / scalability metadata OBU**: 空間・時間スケーラビリティ(L1T2, L2T1 等の層テンプレート)を**ビットストリーム内で宣言**できる。VP9 にも libvpx 実装上の SVC はあるが、層構造をストリーム内でシグナリングする規格的手段がなく、SFU や中間ノードが「どの層を落とせばよいか」を外向きに知る方法が標準化されていない(AV1 は RTP の Dependency Descriptor と対になる)。
- **switch frame (SFRAME)**: キーフレーム同等サイズのインターフレームで、「キーフレーム無しに参照を完全リセット」できる機構。シーク・アダプティブ切替・低遅延復帰に効く。VP9 に相当物なし(キーフレーム挿入しかない)。
- **order_hint**: 全フレームが表示順のヒントを持ち、参照関係を「差分距離」として解釈できる。スキップされたフレームの再構成、層間引き、倍速再生の各ロジックが書ける。VP9 に相当するフレーム序数機構はない。

### 静止画としての第一級サポート

- シーケンスヘッダの **`still_picture` フラグ**と **`reduced_still_picture_header`** は「このストリームは 1 フレーム」を規格で明示する機構で、AVIF の土台になっている。VP9 に静止画用の構文はなく、そもそも VP9 を画像フォーマット化した規格も存在しない(WebP は VP8 系)。
- stillcast の文脈では、**AV1 側は「静止画」が規格の想定ユースケースに入っている**のに対し、VP9 は show_existing_frame を持ちつつも「静止画ビデオ」自体は規格外の応用、という立ち位置の差がある。

## 3. エンコード実践・エコシステム層

| 項目 | AV1 | VP9 |
|---|---|---|
| エンコーダ | libaom(参照実装)、SVT-AV1(速度重視、Intel/Netflix 系)、rav1e(Rust)の 3 系統が競争 | libvpx 系一本(実質メンテナンスフェーズ) |
| HW エンコード | Intel Arc/データセンター GPU、NVIDIA Ada 世代 NVENC、AMD RDNA3+、MediaTek/Qualcomm 上位 SoC が搭載 | 民生 HW エンコード事実上なし(デコード専用が大半) |
| デコーダ | dav1d(高速・WASM 含む)+ libgav1 + HW デコードが 2020 年以降の機器に浸透 | libvpx + HW デコードは 2014 年以降浸透(旧機器互換は VP9 の強み) |
| コンテナ | mp4 `av01`、WebM、IVF、Annex-B、CMAF/DASH/HLS 全対応 | WebM `V_VP9` が本命、mp4 `vp09` は実質 YouTube 系のみ |
| 静止画 | **AVIF**(HEIF ベース、主要ブラウザ対応) | なし |
| リアルタイム | WebRTC AV1(画面共有モード)、Dependency Descriptor で SFU 対応が規格側から支えられる | libvpx の rt プリセットは軽いが、ツールセットが古い |

- **エンコード速度/品質のフロンティア**: SVT-AV1 の高速プリセットは libvpx-vp9 の同等プリセットより同速度で良い画質を出せる報告が多く、「AV1 は遅い」は libaom 低速プリセットの記憶に依存した古い知識になりつつある。競争実装が 3 系統あることが将来の改善余地そのもの。
- **HW エンコードの有無は実用上最大級の差**で、ゲーム録画・ライブ配信・端末内生成(投稿用動画の端末内エンコード)は VP9 では原理的に到達できない領域。

## 4. ユースケース別の写像

| 実用ユースケース | AV1 の武器 | VP9 での到達可否 |
|---|---|---|
| 映画・ドラマ配信(低〜中ビットレート) | フィルムグレイン合成 + CDEF/LR | 粒子保持・帯域内修復が不可能 |
| HDR10/HLG/DV/HDR10+ 配信 | 色情報 + MDCV/CLL + T.35 | 規格内に HDR 搬送路なし |
| 画面共有・リモート UI・講義録画 | palette + intrabc | 文字が滲む、または高レート必須 |
| ビデオ会議 SFU(SVC) | scalability metadata + DD + operating points | 実装依存、層信号の標準なし |
| ライブ配信・ゲーム録画 | HW エンコード、SVT-AV1 rt | ソフトウェアのみ |
| 静止画配信 | AVIF + still_picture/reduced ヘッダ | 相当規格なし |
| 放送・規格準拠が要る配信 | decoder model + timing info | バッファモデル無し |
| 階層 GOP・シーク高速化 | 7 参照 + order_hint + SFRAME | 3 参照固定、復帰点はキーフレームのみ |
| 低ビットレート UGC(縦動画等) | 修復フィルタ群で劣化が緩やか | ブロック/リンギング劣化が顕在化 |
| stillcast 的な超軽量静止動画 | SE + OBU メタ + HDR + AVIF 親和性 | SE あり・構造はむしろ単純(下記) |

## 5. 逆方向:VP9 が残る・むしろ得意な領域

正直に列挙すると:

- **旧世代ハードウェア互換**: 2014〜2019 年頃の TV・STB・モバイルは VP9 デコードを持つが AV1 を持たない。「全世帯到達」系では VP9 がいまだ安全側。
- **構造の単純さ**: 型付きユニット層・seq header・decoder model といった「重いフレームワーク」がないため、stillcast 的なビット列手術は VP9 の方が書きやすい(SE パケット 1 バイト、golden 管理不要 —— cross-codec.md の実測どおり)。
- **ソフトウェアエンコードの軽さ**: libvpx-vp9 の rt プリセットは枯れて軽量。AV1 rt は改善したが最小構成の計算量はまだ VP9 が有利な場面がある。
- **実装の枯れ度**: 長年のデコーダ実装差分・バグ回避ノウハウが蓄積済み。

つまり VP9 の優位は「規格・ツールの新しさ」ではなく **互換性・単純さ・枯れ度** の 3 点に集約される。

## 6. stillcast への含意

- `show_existing_frame` は両者に存在するので、中核トリックの優位はどちらにも転ばない。**AV1 を主力にする理由はむしろ周辺**: OBU メタデータ層(将来のチャプター/字幕/サムネイル差し込みの器)、HDR 搬送、still_picture 規格サポート、AVIF との資産共有(1 枚目のキーフレームを AVIF としても出せる)、エンコーダの品質と選択肢、HW エンコード経路。
- VP9 版の価値は「AV1 非搭載の旧デバイスへの到達」にほぼ限定される。逆に言えば、旧機器をターゲットにしない限り、規格・ツール・エコシステムの全層で AV1 が上位集合に近い。
- AV1 固有でまだ stillcast が使っていない機会: SFRAME による非キーフレーム復帰点(シーク粒度とサイズのトレードオフ改善)、グローバルモーションによる「パン・ズーム演出付き静止画」、metadata OBU による字幕/サムネイル同梱。
